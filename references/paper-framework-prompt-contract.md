# 论文框架图模式 · Prompt 契约

> 核心思路：把「画一张框架图」从散文描述，改写成**可逐条检查的规格书**，在生图**之前**审完。
> 上游的表述是「契约规范下的随机之美」—— prompt 是契约，生图是执行；契约审好了，多试几次总有好图。

## 0. 为什么审在生图之前

S2/S5 是**只负责执行**的图像阶段，不承担重新规划、排序或终审。真正的修复发生在 S1/S4 的 prompt 包阶段：
如果 prompt 里有源证据、箭头方向、变量位置、文字白名单、重复流程或负约束问题，**先修 prompt，再进生图**。

---

## 1. 贡献类型 → 视觉主线（先定这个，再谈画法）

每个 prompt 包必须先判定论文的**主要贡献类型**，再决定视觉主线：

| 贡献类型 | 视觉主线 |
|---|---|
| method / process | 主机制链（输入/上下文 → 操作/变换 → 输出/效果）居中 |
| architecture / module | 模块拓扑 + 层次 |
| system / interaction | 参与者 + 交互时序 |
| model-state / update | 状态与更新环 |
| **data / dataset / database / retrieval / generation / governance / pipeline** | **数据流可以作为主脊** |
| evaluation / benchmark | 评测流程 + 指标归属 |
| hybrid | 取一个主，其余降为支撑 |

**硬规则**：**只有当贡献本身就是关于数据构造、数据管理、检索、生成、治理或流水线设计时，数据流才可以当主视觉脊**。
否则数据标签必须**紧凑、辅助**，不得让数据流主导画面。

同时记录：
- `primary_reader_question` —— 审稿人第一眼要回答的那个问题（**只能有一个**）
- `visual_mainline_decision` —— 主线是什么，为什么
- `data_flow_mainline_justification` —— 若数据流当主脊，写出源证据

---

## 2. 语义图 vs 渲染图 分离

先把论文语义抽成一张**语义图**（节点、边、方向、承载量），再映射成**渲染图**（形状、颜色、图标、位置）。
两张图分开写，不混。混写的后果是「画得好看但语义错了」，而这类错误在图上不可见。

**非模块元素不得升级成同级模块盒子**：变量、指标、权重、阈值、概率、精度、损失、模型参数、符号、公式 —— 这些属于**非同级视觉角色**，默认放在线 / port / fork / merge / tag 上。

---

## 3. 连线：每条都要有证据 + 有消费者

### 3.1 端点到证据

每条箭头/连线，S1/S4 必须能指出**上下游两端**在论文/材料里的证据锚点。

### 3.2 消费者 / 变换者账本（`data_consumer_transformer_ledger`）

对每条承载量 `x` 的边，必须能指出 `x` 的**真实消费者或变换者**。

### 3.3 禁止假中继（no false relay）—— 最常被违反的一条

> 若 A 产出 `x`，C 消费 `x`，而 B **不使用、不变换、不过滤、不存储、不路由** `x`
> → **不得**画 `A -> B` 并标注它承载 `x`。

正确做法：画 `A -> C`；或把 `x` 挂到 C 的输入/port/tag 上；或当直连会让图变乱时，把 `x` 移到 caption/legend。

### 3.4 连接线合并（`connector_bundling_plan`）

两个**块级模块**之间**默认一条合并连线**，除非存在**不同的、有标注的**量需要多条线。
同一含义的多条平行线 = prompt blocker。

### 3.5 方向必须有源

箭头方向来自论文证据，不来自「常见画法」。

---

## 4. 核心机制：不能只画结果，要画操作

对每个有源证据的核心机制，必须保留最小的 **输入/上下文 → 操作/变换 → 输出/效果** 链，并且**落在正确的模块、阶段、循环、路径或层上**。

> 一个可见的输出、状态、结构、决策、信号、材料、配置或效果，**单独出现不足以**覆盖产生、选择、变换、校验、路由、应用或更新它的那个**操作**。

即：**只画「结果长什么样」不够，得画「它怎么来的」**。缺失定位的核心操作 = prompt blocker。

---

## 5. 模块化，不碎片化（`modularity_not_fragmentation_gate`）

这条**跨所有风格**成立：正式出版 schematic、低保真草图、蓝图、科学插画、故事板、信息图板 —— 表面可以不同，但图必须仍是一张**模块化的论文框架图**，而不是一堆微面板拼贴。

---

## 6. 内部机制：用简单通用约定（`simple_internal_motif_gate`）

子模块内部用**审稿人一眼认得的简单约定**：

| 约定 | 用途 |
|---|---|
| 过程步骤 token | 顺序操作 |
| 状态/结构变化标记 | 变换 |
| 度量 tag | 指标 |
| 决策门 | 分支 |
| 合并/分叉提示 | fork / merge |
| 分数/证据 tag | 评测 |
| 轻量反馈/更新环 | 迭代 |

**不得**把子模块内部做成**第二个完整算法**。核心模块不能是空标题盒或项目符号列表。

---

## 7. 密度与背景预算

| 预算项 | 规则 |
|---|---|
| `canvas_area_budget` | 主方法内容占**中心视觉场与主要面积** |
| `context_inset_budget` | 背景/拓扑上下文**从属**，小 |
| `mainline_center_of_gravity_gate` | 视觉重心落在主线上，不得偏移 |
| `layout_information_density_plan` | 紧凑但可读的 manuscript density |

**Prompt blocker**：大面积空白象限、上方顶重的背景知识横幅、散点式微模块岛 —— 除非记录了物理布局例外。

---

## 8. 冗余预算（`redundancy_budget`）

- **不重复的完整 workflow**
- **不重复的 inset / 详图面板**
- 详图面板必须带来**新信息**（`detail_panel_new_information_audit`），不得是主图的放大重播

---

## 9. 可见文字白名单（`visible_text_contract`）

先决定**哪些信息留在图里、哪些交给 caption / legend / 正文**。图内文字按白名单出现，不即兴加字。

---

## 10. 线型语义预算（用虚线/放大/剖面/详图时必读）

只要 prompt 里出现虚线/点线、反馈/交换/复用连接、放大、剖面、inset、机制条、详图面板，就必须额外记录：

| 字段 | 约束 |
|---|---|
| `connector_style_semantic_budget` | 每种线型只承担一种语义 |
| `dashed_line_budget` | 虚线数量有上限，不得装饰性使用 |
| `routing_geometry_contract` | 走线几何（绕行、跨桥、贴边） |
| `callout_abstraction_contract` | 抽象主框架模块 vs 其详图/放大视图必须分开 |
| `detail_panel_new_information_audit` | 详图必须带来新信息 |
| `main_detail_nonduplication_gate` | 主图与详图不得重复 |

**S3 审图时对应记入 issue ledger 的违规项**：`meaningless_dashed_line`、`line_style_semantic_overload`、`floating_or_unanchored_connector`、`long_auxiliary_rail`、`main_detail_duplicate`、`foreign_detail_import`、`callout_as_flow_error`。

---

## 11. 审计循环

S1 与 S4 对每个 prompt 包做**严格契约审核，最多 5 轮修复**。第 5 轮后仍有 blocker → **停止在文本 checkpoint / 残余风险账本**，不得进入 S2/S5 生图。

审核清单（逐条过）：

1. 贡献类型视觉优先级
2. 连线证据账本
3. 连接线重复/合并检查
4. 数据消费者/变换者账本
5. **假中继数据流检查**
6. 变量位置检查（是否被错画成模块盒子）
7. 模块化不碎片化
8. 内部机制简洁性
9. workflow 冗余
10. 背景/上下文预算
11. 线型语义预算（若用到虚线/详图）
12. 布局密度 / 画布面积 / 视觉重心
13. 可见文字白名单
14. prompt 自相矛盾审计

---

## 12. 交付前源保真表

S1/S4 交给生图之前，每个 prompt 包必须附一张**源保真表**，覆盖：可见实体、标签、符号、箭头/线、推理得到的关系。

每一条必须标为四者之一：

| 标记 | 含义 |
|---|---|
| `direct_source` | 论文/材料直接给出 |
| `strict_logical_inference` | 由证据严格推理得出（**必须写明前提与推理链**） |
| `remove` | 删掉（阻塞交付） |
| `revise` | 改写（阻塞交付） |

只要存在 `remove` / `revise`，**阻塞交付**，修完再走。

---

## 13. 反模式速查

| 反模式 | 症状 |
|---|---|
| 假中继 | `A→B` 标着 `x`，但 B 不碰 `x` |
| 变量当盒子 | 精度/损失/阈值画成了同级模块 |
| 平行重复线 | 两模块间多条同义线 |
| 碎片化 | 一张图里十几个微面板 |
| 双算法 | 子模块内部又画了一整套流程 |
| 重复 workflow | 同一条流程画了两遍 |
| 空标题盒 | 核心模块只有名字没有内部机制 |
| 只画结果 | 有输出没有产生它的操作 |
| 顶重留白 | 上方一大条背景，下方挤成一团 |
| 装饰虚线 | 虚线不承载语义 |
| 详图重播 | 详图只是主图的放大 |
